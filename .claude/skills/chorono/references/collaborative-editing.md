# Continuing an edited scene

## Read the current source

At the start of every new follow-up editing turn, call `get_scene` against the chosen editor before preparing a script or patch. Confirm the session still represents the intended document; an old session id or a healthy server alone does not establish that. The returned objects, property values, keys, paths, timelines and parent-child relationships are the source of truth. Earlier generated code and chat descriptions explain intent but do not supersede the live scene.

Keep existing ids and edit the requested part in place. Do not remove and rebuild a scene, layer, timeline or path to make it match an earlier script. Rebuilding can discard manual work even when the result looks similar. Replace or delete existing content only within the user's requested scope.

MCP 2.1 enforces one fresh read per source mutation, with one outer read for a whole atomic batch. Read again before another write; a write response is not a reusable authorization. Each read token binds this real client connection, editor session, runtime document and revision. A new ordinary read supersedes the previous available ordinary token in that client/editor; plan-bound tokens remain separate.

## Revisions, plans and retries

- Read `get_scene` and pass its `revision` as `expectedRevision` plus its one-use `readToken` on every source mutation, including undo/redo, imports and loading another project. Source guards also apply to legacy names. For native batches, only the outer call carries authorization; sub-actions use their native payload schemas (`batchInputSchema` from discovery).
- For procedural edits, authorize `run_script` with `dryRun:true`, inspect the plan and `changeSummary`, then commit its `planId` through `apply_script_plan` with the returned plan revision and new plan-bound `readToken`. The ordinary read token was consumed by preparation; no fresh ordinary token can replace the plan token. Do not rerun the code to commit it; that can generate different ids.
- If a revision changes before commit or the plan expires, read the current scene, reconcile the requested change and prepare a new plan. Do not force an old plan onto a new scene or silently raise its expected revision.
- Use a stable `requestId` for each mutation and reuse it only for an identical transport retry. A changed payload or a newly prepared plan needs a new request id. After an uncertain outcome, read the scene before deciding to issue a replacement mutation; a timeout does not prove that the editor rejected the original request. Retry deduplication is bounded and must not be assumed to survive disconnection or server restart.

Missing/stale/foreign source authority returns a structured `error.code` and `error.recovery`. Tokens live for five minutes, are single-use even when an admitted operation later fails, and are never source/animation parameters. An unchanged revision alone is insufficient after document reset or client reconnect. Exact request retries can recover retained results before token validation; results are scoped to the real client connection, not its display name. Read/runtime/playback/export tools do not require source authority. MCP 2.1 also persists optional `scene.authoring` version 1. Its JSON-tuple record keys distinguish layers, tracks, stable key IDs and spline element IDs. Records separate `createdBy`, `lastWriter`, original content `baseWriter`, sparse field writers and optional copy lineage. `get_layer` reports self attribution and group/spline subtree contributions. Inspect the full current snapshot for exact field records; there is no actor setter tool. Browser edits are human, MCP/planner commits agent, merge imports import; missing/evicted/ambiguous records are unknown, never implicitly human. `truncated:true` means incomplete coverage. Copies have their own creation actor and inherited content origins. Undo/redo restores original attribution; complete project load preserves it; runtime outputs omit it. It is descriptive metadata, not authenticated ownership or permission to overwrite another person's work. Do not write Hermes flags into animation parameters or rewrite the ledger yourself.

## Preserve values and metadata outside the edit

Read complete affected records through `layer.data`, `Timeline.data` or `scene.snapshot()`, and use domain getters for spline elements and particle settings. Those reads are detached copies. Prefer focused native commands, domain operations or `layer.patch` to change only the requested fields. Keep unrelated settings and unknown serializable metadata intact; do not reconstruct a record from only its familiar fields.

`layer.patch` recursively merges objects but replaces arrays, scalars and null. `Layer.set` and native `replace_layer_fields` (legacy `patch_object`) shallowly replace nested objects. For example, changing a fill color through a partial `style` object passed to `set` can remove an existing stroke. Use a focused setter or deep patch. When replacing an array is necessary, start from its freshly read complete contents and preserve the other entries and their metadata; prefer element-by-id domain operations when available.

Inspect affected tracks before adding keys. Exact-time key upsert preserves the existing ID, tangents, segment settings and omitted easing; explicit easing changes it. Equality uses 1e-6 ms, so nearby fractional keys remain independent. Ambiguous coincident source keys are rejected. Do not regenerate a complete keyframe array or track to adjust one value. Use a supported focused key edit that retains unspecified fields, or explicitly preserve the current record when the documented operation requires replacement. Stable key and spline-element ids are safer references than array indices or remembered times.

Preserve manual-looking and unattributed values equally unless the request calls for changing them. For example, if the current clock was set to **9:05**, a request to smooth its hand movement keeps **9:05** by default. An explicit request to change the displayed time authorizes that change. Ask only when the requested result materially conflicts with an existing value and the intended choice remains ambiguous; identify the conflicting value and proposed effect instead of asking for general permission to continue.

## Names and hierarchy

Reuse existing objects and meaningful groups. Name new layers for their visual or functional role, and place related new objects under an appropriate parent when that structure helps editing. Use returned ids in later calls; names are display labels, and `scene.find(name)` returns the first match rather than proving uniqueness or authorship.

Use `scene.explorer` to inspect the actual tree and perform structured rename, group, reorder or reparent operations. Preserve an existing user's naming and hierarchy unless changing them serves the request. Explorer reparent preserves world placement by default and reports unsupported animated or lossy cases; raw `Layer.parent` only changes the parent relationship. Follow [domains.md](domains.md) for the exact hierarchy contracts. Do not reorganize unrelated layers or bypass a hierarchy limitation to complete an otherwise narrow edit.

Committed source changes return a bounded `changeSummary` of layer ids, changed paths and key ids; `truncated:true` means it is partial. It is not a complete audit log or ownership record. After the focused edit, inspect real previews at relevant times, validate and save through the main skill's delivery workflow. Report what changed and any unresolved conflict or exporter warning. Attribution is implemented; semantic conflict/approval policy is not automatically inferred from actor labels.
